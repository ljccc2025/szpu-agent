# M21 测试与质量保障（覆盖率门槛 + 持续集成）实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。

**目标：** 给项目装上可度量、可自动执行的质量门禁——覆盖率量化 + GitHub Actions 每次推送自动跑全量测试。

**架构：** 三件事分开做，互不阻塞——① 依赖拆分（运行 vs 测试），② 覆盖率配置与门槛，③ CI 工作流。前两件在本地即可验证，第三件必须推到 GitHub 真实跑绿才算数。

**技术栈：** `pytest-cov` 7.1、`coverage` 7.16、`pyproject.toml`（PEP 518）、GitHub Actions（`actions/setup-python` 内置 pip 缓存）。

## 设计决策记录

| 冲突 / 待定 | 本计划采用 | 理由 |
| --- | --- | --- |
| 门槛定多少 | **`fail_under = 85`** | 本地实测 89%、CI 预计约 93%。门槛是「防倒退的地板」而不是虚荣指标；定 85 能让本地与 CI 用同一个数字且都不会因为几行注释波动就误报 |
| 门槛基准取本地还是 CI | **取本地（较低的那个）** | 同一个 `fail_under` 要在两个环境都成立，必须迁就低的一侧，否则本地跑覆盖率会莫名其妙失败 |
| 配置文件放哪 | **新建 `pyproject.toml`** | 项目此前没有任何 pytest/coverage 配置文件。`pyproject.toml` 是 PEP 518 现行标准，pytest 与 coverage 都原生支持，一个文件收敛两套配置 |
| 测试依赖 | **拆出 `requirements-dev.txt`** | 现有 `requirements.txt` 把 `pytest`、`httpx` 混在运行依赖里；拆开后 M22 做 Docker 镜像可以只装运行依赖，直接瘦身 |
| CI 装哪些依赖 | **完整依赖 + CPU-only torch 索引** | `sentence-transformers` 默认拉 CUDA 版 torch 约 2.5GB；改用 `download.pytorch.org/whl/cpu` 降到约 200MB。这样 3 个 vectorstore 测试能真跑，又不会拖垮 CI |
| 真实 API 测试 | **CI 不注入 Key** | 保持 skip。CI 不应消耗自费 API 额度，也不该因为上游服务抖动而变红 |
| 覆盖率范围 | **`--cov=app`，不含 `tests/`** | 量的是产品代码被测到多少，把测试自身算进去会虚高 |

## 任务 1：补齐 llm.py 的测试缺口（TDD）

**文件：** 修改 `tests/test_llm.py`

覆盖率报告指出 `complete()` 的重试逻辑从未被执行过——这是线上真会走的路径（网络抖动、限流），不是死代码。

- [ ] **步骤 1：编写失败的测试**
      ① `complete()` 首次成功即返回，不重试；
      ② 前两次抛异常、第三次成功 → 返回成功结果且 `sleep` 被调用 2 次（`monkeypatch` 掉 `time.sleep`，不真等）；
      ③ 三次全失败 → 抛出最后一个异常；
      ④ `tools` 与 `response_format` 被正确透传；
      ⑤ `feed()` 收到没有 `function` 字段的分片不崩（覆盖 45 行）；
      ⑥ `stream()` 收到 `delta` 为 None 的 chunk 时跳过（覆盖 117 行）。
- [ ] **步骤 2：确认测试失败**（新测试尚无对应断言支撑时应为红）
- [ ] **步骤 3：跑测试确认转绿**，并复测 `app/llm.py` 覆盖率应从 72% 升到接近 100%
