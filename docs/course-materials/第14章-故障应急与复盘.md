# 第14章 故障应急响应与复盘

《Linux 系统管理与运维》课程讲义 · 深圳职业技术大学

## 14.1 核心概念

- **止损优先原则**：故障处理的第一目标是恢复服务，不是找到根因。回滚、切流、重启、降级都是合法的第一动作，根因留给复盘。
- **故障等级**：按影响面定级，如 P0（核心功能全量不可用）、P1（核心功能部分受损）、P2（非核心功能异常）。等级决定响应时限与升级路径。
- **战时指挥官（Incident Commander）**：重大故障必须指定唯一指挥官，负责分工与决策；其他人只做两件事——执行指令、同步信息，避免"十个人各改各的"。
- **无指责复盘（Blameless Postmortem）**：复盘针对流程与系统缺陷，不追究个人。惩罚文化只会让下一次故障被隐瞒得更久。

## 14.2 关键知识点

1. 应急响应标准流程：发现（告警/客诉）→ 定级并拉群 → 指定指挥官 → 止损动作 → 每 15~30 分钟对外同步进展 → 恢复确认 → 48 小时内产出复盘报告。
2. 快速定位三问：最近变更了什么（80% 的故障由变更引起，先查发布与配置变更记录）？影响范围是全部还是部分（全部指向共享组件，部分指向个别节点）？监控指标从哪一刻开始劣化（与变更时间线对齐）？
3. 常用止损手段库：版本回滚、流量切换（切机房/切从库）、服务降级（关非核心功能）、限流（保住部分用户可用）、扩容（资源型故障）、重启（内存泄漏类争取时间）。
4. MTTR 拆解：故障总时长 = 发现时间 + 定位时间 + 恢复时间。发现慢补监控告警，定位慢补可观测性与预案，恢复慢补自动化（一键回滚、一键切流）。
5. 复盘报告五要素：时间线（精确到分钟）、影响面（用户数/订单数/资损）、根因（用 5 Whys 追到底层，"操作失误"不是根因，缺少防呆机制才是）、止损过程评估、行动项（每条有 owner 和截止日期）。
6. 行动项闭环：复盘产出的改进项进入任务系统跟踪，每月检查完成率；只复盘不落地等于白开会。
7. 预案与演练：核心场景（主库宕机、机房断网、缓存全挂）必须有书面预案，并通过混沌工程定期实际演练——没演练过的预案等于没有预案。

## 14.4 典型实践场景与最佳实践

### 场景一：一次 P0 故障的标准处置
支付成功率跌至 60% 触发 P0 → 5 分钟内拉群并指定指挥官 → 查变更记录发现 20 分钟前网关发过版本 → 立即回滚，10 分钟恢复 → 复盘发现新版本连接池参数配错，行动项：连接池参数纳入发布前自动检查。

### 场景二：值班体系建设
主备双值班制，P0 告警 5 分钟未响应自动升级到备份值班与上级；值班工程师必须具备执行全部一键预案的权限，避免"半夜找不到有权限的人"。
