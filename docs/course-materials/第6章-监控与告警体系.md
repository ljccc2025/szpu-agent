# 第6章 监控与告警体系

《Linux 系统管理与运维》课程讲义 · 深圳职业技术大学

## 6.1 核心概念

- **可观测性三大支柱**：指标（Metrics）、日志（Logs）、链路（Traces）。本章聚焦指标，日志见第7章。
- **四大黄金信号**（Google SRE 提出）：延迟（Latency）、流量（Traffic）、错误（Errors）、饱和度（Saturation），是服务监控的最小完备集。
- **Pull 与 Push 模型**：Prometheus 主动拉取（Pull）exporter 暴露的 /metrics 端点；Push 模型（如 Pushgateway、StatsD）适合短生命周期任务。
- **告警疲劳**：无效告警过多导致值班人员麻木、漏掉真故障，是告警体系设计的头号敌人。

## 6.2 关键知识点

1. 指标四种类型：Counter（只增计数器，如请求总数）、Gauge（可增可减，如内存使用）、Histogram（分桶统计，如延迟分布）、Summary（分位数）。
2. 分位数比平均值更能反映用户体验：P99 延迟 2s 意味着 1% 的请求慢于 2s，平均值会掩盖长尾。
3. 告警必须分级：P0（电话叫醒，服务不可用）、P1（即时消息，核心指标劣化）、P2（工单，次日处理）。每条告警都应有明确的处理动作，"仅供参考"的告警应删除。
4. 告警降噪三板斧：分组（group_by 把同类告警合并）、抑制（inhibit，主机宕机时抑制其上所有服务告警）、静默（silence，变更窗口内临时屏蔽）。
5. 基于症状告警优于基于原因告警：对"用户请求错误率升高"告警，而不是对"某台机器 CPU 高"告警——后者可能根本不影响用户。
6. Exporter 生态：node_exporter（主机）、mysqld_exporter（数据库）、blackbox_exporter（拨测 HTTP/TCP/ICMP）。
7. 记录规则（Recording Rules）预计算高频查询，避免大盘打开时实时聚合拖垮 Prometheus。

## 6.3 常用工具与技术栈

| 工具 | 用途 |
|------|------|
| Prometheus | 时序数据库 + 拉取式采集 + PromQL 查询 |
| Grafana | 可视化大盘与多数据源整合 |
| Alertmanager | 告警路由、分组、抑制、静默 |
| Zabbix | 传统企业级监控，agent 模式，自带告警 |
| 夜莺 Nightingale | 国产开源监控，兼容 Prometheus 生态 |

## 6.4 典型实践场景与最佳实践

### 场景一：新服务接入监控的标准清单
上线前必须完成：暴露 /metrics 端点、接入四大黄金信号大盘、配置 P0/P1 告警并指定值班人、编写告警处理手册（Runbook）链接进告警内容。

### 场景二：告警治理专项
每月统计告警量 Top10 的规则，对一周内触发超过 50 次但从未处理的告警，要么修阈值、要么改成工单、要么直接删除，把值班群告警量压到每天 10 条以内。
