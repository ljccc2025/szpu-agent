# 第7章 日志管理与分析

《Linux 系统管理与运维》课程讲义 · 深圳职业技术大学

## 7.1 核心概念

- **集中式日志**：把散落在各台服务器上的日志统一采集到中心平台检索，避免故障时逐台机器 grep。
- **结构化日志**：以 JSON 等格式输出固定字段（time、level、trace_id、msg），机器可解析，检索效率远高于纯文本。
- **日志管道四阶段**：采集（Agent）→ 传输缓冲（消息队列）→ 存储索引 → 查询展示。
- **索引与保留策略**：日志量大、价值随时间衰减，需按天滚动索引并设置分层保留（热数据 7 天 SSD、温数据 30 天、冷数据归档对象存储）。

## 7.2 关键知识点

1. 日志级别规范：DEBUG（开发调试）、INFO（关键业务动作）、WARN（可自愈异常）、ERROR（需要人工关注）。生产环境默认 INFO，ERROR 必须可告警。
2. trace_id 全链路串联：入口网关生成唯一 trace_id 并透传到每个下游服务的日志中，一次检索即可还原整条调用链路。
3. 采集端选型：Filebeat 轻量（Go 编写，占用低）适合大规模部署；Fluent Bit 更省资源，云原生场景常用；Logstash 功能强但重，适合做中心解析层。
4. 高峰期削峰：采集端与存储之间加 Kafka 缓冲，日志洪峰时不丢数据、不打挂 Elasticsearch。
5. Loki 与 ELK 的取舍：Loki 只索引标签不索引全文，存储成本约为 ES 的十分之一，适合"按服务+时间段查日志"；ELK 支持全文检索与复杂聚合，适合安全审计与业务分析。
6. 敏感信息脱敏：手机号、身份证、密码等必须在采集或入库前脱敏，这是合规硬性要求（详见第16章）。
7. 日志与指标联动：从 Grafana 大盘发现错误率飙升后，应能一键跳转到对应时间段、对应服务的日志上下文。

## 7.3 常用工具与技术栈

| 工具 | 用途 |
|------|------|
| Elasticsearch + Kibana | 全文索引存储与查询界面（ELK 核心） |
| Filebeat / Fluent Bit | 部署在各节点的轻量日志采集器 |
| Grafana Loki | 低成本标签索引日志系统，与 Grafana 原生集成 |
| Kafka | 日志传输层削峰缓冲 |

## 7.4 典型实践场景与最佳实践

### 场景一：一次 502 故障的日志定位
用户报 502 → 在 Kibana 按 `status:502 AND host:网关` 过滤锁定时间段 → 取一条请求的 trace_id → 用 trace_id 全局检索 → 发现卡在下游库存服务连接池耗尽，10 分钟内定位根因。

### 场景二：日志成本治理
统计各服务日均日志量，对 Top 服务推动三件事：DEBUG 日志禁止上生产、重复堆栈采样输出（如每 100 条打 1 条）、访问日志改用 Loki 存储，整体日志成本可下降 50% 以上。
