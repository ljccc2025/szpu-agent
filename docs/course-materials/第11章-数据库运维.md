# 第11章 数据库运维

《Linux 系统管理与运维》课程讲义 · 深圳职业技术大学

## 11.1 核心概念

- **主从复制**：主库把变更写入 binlog，从库拉取并重放，实现读写分离与故障接管；默认异步复制存在丢数据窗口，半同步复制要求至少一个从库确认后才提交。
- **备份两大类型**：逻辑备份（mysqldump 导出 SQL，体积小、恢复慢、可跨版本）与物理备份（XtraBackup 拷贝数据文件，速度快、适合大库）。
- **时间点恢复（PITR）**：全量备份 + 持续归档的 binlog，可把数据库恢复到任意时刻（如误删表前 1 秒）。
- **连接池**：数据库连接创建昂贵且总数有限，应用侧必须用连接池复用连接，防止连接风暴打挂数据库。

## 11.2 关键知识点

1. 慢查询治理闭环：开启 slow_query_log（阈值建议 1 秒）→ 每周分析 Top 慢 SQL → `EXPLAIN` 查看执行计划 → 加索引或改写 SQL → 回归验证。
2. 索引三原则：最左前缀匹配（联合索引 (a,b,c) 只能命中以 a 开头的查询）、区分度优先（性别列不值得建索引）、避免在索引列上做函数运算导致索引失效。
3. 主从延迟排查：`SHOW SLAVE STATUS` 看 Seconds_Behind_Master；常见原因是大事务（一次 update 百万行）、从库单线程重放、从库硬件弱，对应解法是拆小事务、开并行复制。
4. 高可用方案：MHA、Orchestrator 实现主库故障自动切换；切换的关键是避免脑裂——旧主复活后必须先隔离再降级为从。
5. binlog 三种格式：statement（记 SQL，可能主从不一致）、row（记行变更，最安全，生产标准）、mixed；PITR 与数据订阅都依赖 row 格式。
6. Redis 运维要点：持久化选 RDB（快照、恢复快）还是 AOF（追加日志、丢数据少）需按业务取舍；大 key（单 key 超 10MB）与热 key 是线上抖动主因，用 `redis-cli --bigkeys` 定期巡检。
7. 数据库变更规范：大表 DDL 用 gh-ost/pt-online-schema-change 在线变更，避免锁表；所有变更走工单并在低峰执行。

## 11.3 常用工具与技术栈

| 工具 | 用途 |
|------|------|
| mysqldump / XtraBackup | 逻辑备份 / 物理热备份 |
| Orchestrator | MySQL 拓扑管理与自动故障切换 |
| pt-toolkit (Percona) | 在线 DDL、慢查询分析、主从校验 |
| DBeaver / Navicat | 图形化管理与审计入口 |

## 11.4 典型实践场景与最佳实践

### 场景一：误删数据的时间点恢复
开发误执行 `DELETE` 未带 WHERE → 立即停止写入并记录当前时刻 → 找到最近一次全量备份恢复到临时实例 → 重放 binlog 至误操作前 1 秒 → 校验数据后回导生产。整个过程的前提是：备份可用且 binlog 完整，这就是为什么必须做恢复演练。

### 场景二：读写分离下的延迟兜底
"下单后立刻查订单查不到"多为主从延迟所致。方案：写后短时间内的读强制走主库（会话粘滞），或对延迟敏感的查询永远走主库，从库只承接报表与列表页。
