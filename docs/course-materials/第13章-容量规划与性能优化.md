# 第13章 容量规划与性能优化

《Linux 系统管理与运维》课程讲义 · 深圳职业技术大学

## 13.1 核心概念

- **容量规划**：回答"现有资源还能扛多久、大促要扩多少"两个问题，核心输入是业务增长预测与单机容量基线。
- **USE 方法**：对每类资源检查利用率（Utilization）、饱和度（Saturation）、错误（Errors），是主机层性能分析的系统化方法（服务层的四大黄金信号见第6章）。
- **单机容量基线**：通过压测得出单实例在满足延迟 SLO 前提下的最大 QPS，是一切扩容计算的基础，每次大版本后需重新校准。
- **水位线管理**：日常水位建议 50%~60%，既留出突发余量与故障冗余（N+1），又不至于严重浪费（成本视角见第18章）。

## 13.2 关键知识点

1. 峰值估算公式：预估峰值 QPS = 日请求量 × 峰值集中系数 / 峰值时长秒数；所需实例数 = 峰值 QPS / 单机基线 QPS × 冗余系数（一般 1.5）。
2. 压测三种模式：基准压测（单接口找单机极限）、容量压测（逐步加压找系统拐点）、全链路压测（真实流量模型 + 影子库，验证整体容量）。
3. 性能拐点识别：加压过程中吞吐不再线性增长而延迟陡增的点即拐点，生产容量按拐点的 70% 规划。
4. 主机层快速诊断：CPU 高先分清 us（应用计算）/sy（系统调用）/wa（等 IO）/si（软中断）；`vmstat`、`iostat -x`、`sar` 三件套 60 秒判断瓶颈在 CPU、内存、磁盘还是网络。
5. 应用层常见瓶颈排序：数据库慢查询 > 外部依赖串行调用 > 锁竞争 > GC 停顿 > 代码算法。优化优先级永远从耗时占比最大处入手，避免"优化了 1% 的热点"。
6. 缓存是第一性能杠杆：接口加一层 Redis 缓存往往比任何代码优化收益都大，但必须同时设计缓存穿透（空值缓存）、击穿（互斥重建）、雪崩（过期时间加随机抖动）防护。
7. 扩容决策树：无状态服务优先水平扩容（加实例）；数据库先垂直升配再考虑分库分表；队列消费慢则加消费者并检查分区数是否成为上限。

## 13.4 典型实践场景与最佳实践

### 场景一：大促容量保障流程
提前 1 个月拿到业务预估峰值 → 全链路压测验证当前容量 → 按公式扩容并预留 N+1 → 压测复验 → 大促当天值守并准备好一键扩容与降级预案（非核心功能开关降级）。

### 场景二：一次接口延迟优化
P99 从 1.2s 降到 180ms 的路径：链路追踪发现 70% 耗时在一条未走索引的 SQL → 加联合索引后降到 400ms → 再把三个串行外部调用改并行，最终 180ms。先测量、再优化、每步验证。
