# 第9章 配置管理与基础设施即代码（IaC）

《Linux 系统管理与运维》课程讲义 · 深圳职业技术大学

## 9.1 核心概念

- **基础设施即代码（IaC）**：用代码描述服务器、网络、中间件等基础设施，纳入版本控制，变更可评审、可回溯、可重放。
- **声明式与命令式**：命令式描述"怎么做"（执行一串命令）；声明式描述"要什么"（期望状态），由工具自行收敛，是 Terraform/Kubernetes 的核心思想。
- **幂等性**：同一份配置重复执行任意次，结果保持一致。Ansible 模块天然幂等（如 `state=present`），而裸 shell 脚本通常不幂等。
- **配置漂移（Drift）**：有人绕过代码直接登录服务器改配置，导致实际状态偏离代码描述，是 IaC 体系最大的敌人。

## 9.2 关键知识点

1. Ansible 无 agent 架构：通过 SSH 推送任务，被管节点只需 Python，接入成本几乎为零；核心对象为 Inventory（主机清单）、Playbook（剧本）、Role（可复用角色）。
2. Terraform 工作流三步：`terraform plan` 预览变更 → 评审 → `terraform apply` 执行；state 文件记录资源映射，必须存放远端（如对象存储）并加锁，禁止提交到 Git。
3. 可变与不可变基础设施：可变模式在原服务器上升级打补丁；不可变模式每次变更都构建新镜像、起新机器、下线旧机器，彻底消灭配置漂移。
4. 配置与代码分离：应用配置按环境注入（环境变量 / 配置中心），同一制品跑遍所有环境；禁止把 IP、密码硬编码进代码。
5. 密钥管理：数据库密码、API Key 绝不明文入库，用 Vault、云 KMS 或 Ansible Vault 加密存储，并建立定期轮换机制。
6. 变更三要素：任何生产配置变更必须有 PR 评审、有灰度顺序（先测试环境后生产）、有回滚方案，"改一行配置"引发的故障不比代码少。
7. 漂移检测：定期执行 `terraform plan` 或 Ansible check 模式比对期望与实际状态，发现漂移立即告警并收敛。

## 9.3 常用工具与技术栈

| 工具 | 用途 |
|------|------|
| Ansible | 无 agent 配置管理与批量运维 |
| Terraform | 多云资源编排，声明式 IaC 事实标准 |
| HashiCorp Vault | 密钥集中管理、动态凭据、自动轮换 |
| Consul / Nacos | 服务发现与动态配置中心 |

## 9.4 典型实践场景与最佳实践

### 场景一：百台服务器批量加固
用 Ansible 编写 hardening Role（改 SSH 端口、禁 root 远程登录、部署审计脚本），先对 5 台金丝雀主机执行并验证，再全量滚动执行，全程 20 分钟且可重复执行无副作用。

### 场景二：新环境一键重建
所有云资源（VPC、主机、负载均衡、数据库）均由 Terraform 管理后,搭建一套完整的预发环境从"手工点两天控制台"变为"apply 一次 40 分钟"，容灾重建能力同步获得。
