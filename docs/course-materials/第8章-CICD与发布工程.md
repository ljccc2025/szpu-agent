# 第8章 CI/CD 与发布工程

《Linux 系统管理与运维》课程讲义 · 深圳职业技术大学

## 8.1 核心概念

- **持续集成（CI）**：代码合入主干即自动构建 + 跑测试，让集成问题在提交当天暴露。
- **持续交付与持续部署（CD）**：持续交付指随时"可以"一键发布到生产；持续部署更进一步，通过全部门禁后"自动"发布，无需人工审批。
- **制品（Artifact）**：一次构建产出的不可变交付物（镜像、jar 包）。同一制品应贯穿测试/预发/生产，禁止"生产单独再打一个包"。
- **发布与部署分离**：部署是把新版本放上服务器，发布是把流量切给它。借助开关（Feature Flag）可以先部署后发布，随时熔断。

## 8.2 关键知识点

1. 标准流水线阶段：代码检查（lint）→ 单元测试 → 构建制品 → 镜像扫描 → 部署测试环境 → 自动化回归 → 人工/自动门禁 → 生产发布。
2. 三大发布策略对比：滚动发布（逐批替换实例，省资源但回滚慢）、蓝绿发布（两套环境瞬间切流，回滚最快但成本翻倍）、金丝雀发布（先放 1%~5% 流量验证，风险最小，主流选择）。
3. 金丝雀评估指标：切流后观察错误率、P99 延迟、核心业务指标（如下单成功率）至少 15~30 分钟，任一指标劣化立即自动回滚。
4. 回滚优先于修复：生产故障时先回滚到上一稳定版本止损，再排查问题，禁止在线上"边猜边改"。
5. 流水线必须幂等可重放：同一 commit 重跑流水线应产出相同结果；构建环境用容器固化，杜绝"在我机器上是好的"。
6. 数据库变更是发布最大风险点：DDL 与代码分开发布，遵循"先加列后用列、先停写再删列"的向前兼容原则。
7. GitOps 模式：以 Git 仓库中的声明式清单为唯一事实来源，Argo CD 持续比对集群实际状态与仓库期望状态并自动收敛。

## 8.3 常用工具与技术栈

| 工具 | 用途 |
|------|------|
| GitLab CI / GitHub Actions | 代码托管一体化流水线 |
| Jenkins | 老牌自建 CI 服务器，插件生态庞大 |
| Argo CD | Kubernetes 场景 GitOps 持续部署 |
| Harbor | 私有镜像仓库，带漏洞扫描与签名 |

## 8.4 典型实践场景与最佳实践

### 场景一：电商核心服务金丝雀发布
新版本先发 1 台（约 2% 流量）→ 自动比对金丝雀实例与存量实例的错误率和延迟 → 15 分钟无劣化则按 10%→50%→100% 逐级放量，全程约 1 小时，任一环节异常一键回滚。

### 场景二：发布窗口与冻结期
大促前一周进入发布冻结，只允许 P0 级修复走紧急通道（需双人审批）；日常发布避开业务高峰，安排在流量低谷时段并保证值班人员在线。
