# 第17章 SRE 与服务质量管理（SLI/SLO/SLA）

《Linux 系统管理与运维》课程讲义 · 深圳职业技术大学

## 17.1 核心概念

- **SRE（站点可靠性工程）**：Google 提出的方法论，用软件工程手段解决运维问题，核心信条是"用自动化消灭重复劳动（Toil）"。
- **SLI（服务水平指标）**：客观度量服务质量的指标，如"成功请求占比""P99 延迟"。SLI 必须站在用户视角选取。
- **SLO（服务水平目标）**：对 SLI 设定的内部目标，如"30 天窗口内可用性 ≥ 99.9%"。SLO 是工程团队的北极星。
- **SLA（服务水平协议）**：对外承诺的 SLO + 违约赔偿条款，是商务合同概念。SLA 通常比内部 SLO 宽松一档（内部 99.95%、对外承诺 99.9%）。
- **错误预算（Error Budget）**：1 − SLO 即允许的不可靠额度。99.9% 的月度错误预算约为 43 分钟不可用时间。

## 17.2 关键知识点

1. 可用性数字直觉：99.9%（三个9）= 每月约 43 分钟不可用；99.99%（四个9）= 每月约 4.3 分钟；每加一个 9，成本大约上一个数量级，盲目追高是浪费（成本视角见第18章）。
2. 错误预算的用法：预算充足时鼓励快速发布新功能；预算耗尽时冻结非必要发布，团队优先做可靠性改进——这为"业务要快"与"运维要稳"的矛盾提供了客观仲裁机制。
3. SLI 选取规范：请求驱动型服务用"成功率 + 延迟分位数"；数据管道用"新鲜度 + 正确性"；存储用"持久性"。指标必须在靠近用户的位置测量（负载均衡层优于应用自报）。
4. Toil 的定义与治理：手动、重复、可自动化、无长期价值的工作（如手工重启、手工扩容）即 Toil；SRE 团队应把 Toil 控制在工作时间 50% 以下，超限即立项自动化。
5. 燃尽告警（Burn Rate Alert）：按错误预算消耗速率告警——1 小时烧掉 2% 预算触发紧急告警，比固定阈值告警更贴近业务影响（与第6章症状告警理念一致）。
6. SLO 评审节奏：每季度回顾 SLO 达成率；长期 100% 达成说明目标太松可收紧，频繁击穿则要么加大可靠性投入、要么承认目标不现实并调整。
7. 运维值班与 SRE：SRE 模式下开发团队共担值班（you build it, you run it），倒逼代码质量与可观测性建设。

## 17.3 常用工具与技术栈

| 工具 | 用途 |
|------|------|
| Prometheus + recording rules | SLI 计算与错误预算燃尽统计 |
| Grafana SLO 插件 / Sloth | SLO 定义、大盘与燃尽告警生成 |
| OpenTelemetry | 统一采集指标/链路/日志的标准框架 |
| Backstage | 服务目录，登记每个服务的 SLO 与负责人 |

## 17.4 典型实践场景与最佳实践

### 场景一：给一个 API 服务落地 SLO
选定 SLI：负载均衡层统计的非 5xx 占比与 P99 延迟 → 参考历史 3 个月数据定 SLO：成功率 99.9%、P99<500ms → 配置燃尽告警（快烧+慢烧双窗口）→ 每季度评审调整。

### 场景二：错误预算仲裁发布冻结
某月两次故障烧掉 90% 错误预算，按事先约定触发发布冻结，团队用两周完成三个可靠性行动项（超时治理、依赖降级开关、扩容），预算窗口滚动恢复后解除冻结。全程无需领导拍板，规则自动生效。
